# Bläkkiskili

Telegram BAC-estimation bot. Bun + TypeScript + grammY + bun:sqlite. See README.md.

## Commands

- `bun test`: unit tests plus `test/bot.test.ts`, which drives the real bot against a fake Telegram API and checks that every message is valid Telegram HTML
- `bun check`: type check (use this rather than `tsc`)
- `bun run dev`: run locally with long polling (needs `.env`)

## Conventions

- Use Bun APIs: `bun:sqlite`, `Bun.serve`, `bun test`. Bun loads `.env` automatically.
- `src/lib/alcomath.ts` must stay numerically identical to the original Bläkkisvuohi's `alcomath.js`. Users compare estimates, and the height-in-cm quirk is compensated by `MAGIC_NUMBER`.
- Services (`src/services/`) take derived keys (HMACs), never raw Telegram IDs, except where the legacy sha256 format is needed for import and export, and an `IdentityRef` where a login is created or linked (it derives the key and stores the encrypted contact). They must not import grammY.
- Accounts vs logins: `profile.id` is the account (drinks, groups, body data). `ctx.kili.identityId` is the Telegram login (`identities` table, see `src/services/identities.ts`), and pending typed input is keyed by it, never by `profile.id`. Create accounts with `accounts.register(ref, …)`; `upsert` alone makes an account no login can reach.
- All messages use `parse_mode: "HTML"`. Build text with `fmt()` from `src/lib/format.ts`, which escapes values. Use `raw()` only for HTML you built yourself.
- Use `ctx.kili.services.deps.now()` for time, not `Date.now()`, so tests can control the clock.
- Schema changes: append a new entry to `MIGRATIONS` in `src/db/index.ts`. Never edit an existing one.
- Menu nodes live in `NODES` in `src/bot/menu.ts`. Callback data is `m:<node>[:<arg>]`, max 64 bytes. Any navigation clears the pending typed-input state unless the node is in `KEEPS_PENDING`.
- Operations (backups, secrets, server, incidents) are documented in `deploy/RUNBOOK.md`. If you change data retention or the backup policy, update the privacy texts in `src/strings.ts` to match.
- `/kuvaaja`: `src/lib/chart.ts` builds the SVG (a pure function, palette validated with the dataviz skill) and `src/lib/render.ts` converts it to PNG with resvg. The Docker image needs `font-dejavu` for text. After layout changes, render a sample and look at it.
- Announcements live in `src/announcements.ts` (Telegram HTML, newest last).
- Alko catalogue: `src/services/products.ts` (load, refresh and search over Alkometriikka's data.minimal.json, columns looked up by name; removed products have a null `Tila`: found by number or EAN, never in search; unknown `Tyyppi` becomes "Muut"), `src/lib/servings.ts` (product → servings with alcohol, kcal and price, the merging of package sizes into one `CatalogDrink`, and the logged description), `src/bot/inline.ts` (inline mode). Drinks picked from the catalogue store `product_id`. Every logging path passes `kcal` to `drinks.add` (the serving's or preset's; null for custom drinks).
- Barcodes: the catalogue's EAN column first (`Products.productIdByEan`), then `src/services/barcodes.ts`, which asks Alkometriikka's API Worker (`GET /gtin/{ean}` → `{id}`, 404 unknown, 429 rate limited per IP, see alkometriikka `docs/api-worker.md`) and caches answers in memory. Nothing user-specific is sent. `src/lib/ean.ts` must accept what the Worker accepts (EAN-8/13; UPC-A is padded to 13). Menu view is `barcodeView` in `menu.ts`; photo decoding is in `src/bot/barcode.ts` and replaced via `BotOptions.barcodeIO` in tests. If you change what is sent to the Worker, update the privacy text in `src/strings.ts`. Lookup order in `barcodeView`: catalogue EAN, then user-added products (`src/services/customproducts.ts`, table `custom_products`, shared by all users, never sent to Alkometriikka), then the Worker. A user-added product becomes a `CatalogDrink` with id `e<ean>` (`customCatalogDrink` in `servings.ts`), so look drinks up with `findDrink` in `menu.ts`, not `products.get`; its drinks store `product_id` NULL (only Alko numbers go there). Users who can't edit a user-added product get "Ilmoita virheestä" (`CustomProducts.report`, table `custom_product_reports`, one open report per user and product, admins never see who reported): a new report messages the admins with `notifyAdmins` in `src/bot/admin.ts` (the website gets it as `WebAppOptions.notifyAdmins`), and admins clear reports on `/admin`. The website does the same lookup in `src/web/api/barcodes.ts` (`/api/barcodes/<ean>`, `PUT`/`DELETE …/product`); keep it in step with `barcodeView`. It decodes camera frames and photos in the browser (`web/src/lib/barcode.ts`) and sends only the number.
- Updates are handled concurrently (`src/bot/polling.ts`, `@grammyjs/runner`), one user's updates in order (`sequentialize` in `createBot`). Never block on slow I/O assuming nothing else runs, but also never assume two handlers of the same user overlap. `test/concurrency.test.ts` guards this; don't switch back to `bot.start()`, which handles one update at a time and froze the bot during a `/data` upload.
- Website: `web/` is a SvelteKit 3 SPA (adapter-static, own `package.json`; `bun run web:build`, `web:check`, `web:demo`), served with the JSON API by the bot's process from `src/web/` (`server.ts`, `static.ts` files and headers, and the API: `app.ts` merges the route tables of `api/*.ts`, one module per area, into `Bun.serve`'s `routes`). A route is `"/api/x/:id": { GET: user((c) => …) }`: handlers are wrapped in the guards they need (`api/guards.ts`: `user`, `admin`, `signedIn`, `screen`, rate limits; area-specific ones like `member` live in their module). Bun's `:params` match any segment and arrive decoded, so check them with `c.param(name, regex)`. Tests call the API through `serveTestApp` in `test/helpers.ts` (a real server on port 0). API types shared with the client are in `shared/api.ts`; keep it dependency-free. Sign-in is `/web` (single-use link, token in the URL fragment) or a redirect to Telegram's login page (oauth.telegram.org, back to `/login#tgAuthResult=…`; not the widget script, whose `eval` the CSP forbids); sessions are in `src/services/websessions.ts` (token hashes only). The API takes the account from the session, never from the request; mutating requests need the `Origin` and `X-Kili` headers. Admin (`/admin`, `/api/admin/*`) is decided per session by `isAdmin` (built in `app.ts`, checked by the `admin` guard): the session's Telegram identity key must be one of `ADMIN_IDS`'s and still belong to the account; `Me.admin` only shows the nav link. Not to be confused with Telegram group admins (`src/web/groupadmins.ts`: `getChatAdministrators`, needs the group's recorded chat id, answers cached 5 min), who may stop any of their group's screen links, as a web group's owner may. The CSP forbids inline styles and scripts (it hashes the one SvelteKit bootstrap script), so use classes and CSS variables, not `style="..."` attributes (Svelte's `style:--x={…}` directive is fine: it sets the property from script). Styling is Tailwind 4 (`@tailwindcss/vite`), utilities in the markup and no `<style>` blocks. `web/src/app.css` replaces Tailwind's palette, type scale and radii with the site's tokens (`bg-surface-2`, `text-secondary`, `border-line`, `text-sm` is 13px on the 14px root…); dark mode redefines those variables, so no `dark:` variants. Its `components` layer has the shared classes: `page`, `card` (+ `card-panel`), `notice`, `btn` (+ `btn-primary`, `btn-danger`, `btn-ghost`, `btn-sm`, `btn-icon`). Number tiles are `#lib/Stat.svelte`. When one element switches between two values of the same property, use a conditional class array (`class={[cond ? "a" : "b"]}`), never both utilities at once. SvelteKit 3 has no `$lib`: use `#lib/...`. Images from elsewhere (Alko product photos, Telegram group photos) are fetched by the server in `src/web/photos.ts` and served from `/api`, so browsers never contact those hosts; the CSP allows only our own images. Web has TypeScript 5 (SvelteKit needs its JS API); the root has 7 and excludes `web/`.
- PWA: `web/static/manifest.webmanifest` (icons `icon-192.png`, `icon-512.png`, upscaled from `kili-256.jpg`) and the service worker `web/src/service-worker/` (SvelteKit registers it). It caches only the app (built files, `static/`, the index.html shell) and never `/api`, so no user data is stored on the device; pages are network first with the shell as the offline/5xx fallback. `static.ts` serves `service-worker.js` with `no-cache` so a deploy reaches installed apps.
- Website texts and data: help, terms and privacy pages (`/help`, `/terms`, `/privacy`, public) are the bot's own texts from `src/strings.ts`, built by `docsHtml` in `src/bot/context.ts` (so bot and site can't drift apart), turned into blocks by `src/web/api/docs.ts` (`GET /api/docs/:page`) and drawn by `web/src/lib/DocPage.svelte`; no HTML reaches the browser. Favourites (`api/favorites.ts`), backdated drinks (`at` in `LogDrinkRequest`, at most a week back), data export (a zip, `src/lib/zip.ts`), import (one raw CSV per request) and account deletion are in `api/account.ts`. Export and import need the Telegram id behind the session's account, which is read from the encrypted contact (`identities.contacts`); an account with no Telegram login gets `no_telegram`. `Bun.serve`'s body limit is 10 MiB for imports; everything else is held to 4 KiB by `readJsonBody`.
